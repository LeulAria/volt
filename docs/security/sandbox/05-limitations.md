# Volt Sandbox: Known Limitations and Future Work

What the sandbox does **not** guarantee today. Each limit comes with the reason, and with its mitigation where there is one.

## Limits of the OS mechanisms

1. **macOS: a fully detached process can outlive its run** (`process.tree` is `partial`).
   - **Why:** macOS has no PID namespace. The kill reaches the process group, every descendant reachable through parent pids, every process still carrying the run's `VOLT_SANDBOX_TAG`, and (through the watchdog) the group when Volt itself dies. The sandbox helper also tracks each run from its root (kqueue fork and exit events) and kills every process the disclaimed root is responsible for, which a double-forked, `setsid`, environment-cleared daemon still is (TREE-MAC-1).
   - **The gap:** a process that does all of that and also disclaims its responsibility again is invisible to all of these.
   - **What still holds:** it stays inside Seatbelt (sandboxes are inherited and cannot be dropped) and inside its rlimits, so it is persistence, not an escape. The adversarial suite checks that such a survivor still cannot write outside.
2. **macOS: process and memory limits are best effort** (`partial`). RLIMIT_NPROC counts every process of the user, and RLIMIT_AS/RSS are not enforced.
   - **Processes:** the run gets RLIMIT_NPROC at the user's count plus its limit, and the helper's fork watchdog stops and kills the whole tree the moment it passes the limit (RES-MAC-2).
   - **Memory:** the tree's physical footprint is polled every second and the tree is killed over the limit (RES-MAC-1), so a fast allocation can pass the limit for up to a second.
3. **Linux: paths that do not exist at launch cannot be guarded** (`filesystem.protectNew` is `partial`). bubblewrap binds existing paths; it cannot deny creating `.vscode/tasks.json` or a new nested `.git` inside a writable workspace.
   - **What still holds:** existing protected paths are read-only binds, and `**/` patterns are expanded at launch over a bounded walk.
   - **Landlock** runs inside bubblewrap where the kernel has it (a second check on reads and writes), but it only grants rights to whole folders, so it cannot carve such holes either (LNX-FS-3 stays open); an overlay with review on exit (the "cells" design) would.
4. **Linux: without a delegated cgroup, memory limits are virtual memory** (RLIMIT_AS). V8 and Wasm reserve far more address space than they use, so a tight value breaks Node.
   - Where systemd's user manager delegates the memory controller (systemd 252+), a run with a memory limit gets its own `systemd-run --user --scope` instead: memory.max on the whole tree, enforced (RES-LNX-1), and no RLIMIT_AS.
5. **Linux specifics.**
   - **Single home files can't be replaced atomically.** Files written in place (`~/.claude.json`) are single-file binds, so an agent that replaces one by rename gets `EBUSY`.
   - **Servers in the sandbox can't be reached from the host.** A server a sandboxed workload starts with `listen` is reachable only inside its network namespace, not from the host's browser.
   - **The sandbox's tmpfs mounts have no size cap.**
   - **No OS denial reports.** The kernel does not report denials the way the macOS log does, so the transcript shows Linux denials only from command output and the proxy.
   - **No ssh-agent.** It is not exposed to Linux agents (F-L7). With the network on, ssh's configs, known hosts and public keys are readable as on macOS (item 8), but a `~/.ssh/config` that is a link (into a dotfiles folder) is not visible at its own name: bubblewrap mounts the link's target, not the link.
   - **Containers need an init.** When Volt runs as PID 1 in a container, run it with an init so finished sandboxes are reaped.
   - **`.env` files deep in a home toolchain may stay readable.** `**/.env` and the other deny patterns are expanded at launch by a bounded walk. The workspace, the writable folders and a readable home must be walked whole, or the run is refused (B-27). With narrow reads the home is not readable, only the toolchains in it (`~/.cargo`, `~/.dotnet`, `~/go`, `~/.local/bin`). Those, and the shared temp folders an agent may write (`/tmp`, `/var/tmp`, `/dev/shm`), are walked after the rest, with what is left of the budget, best effort: a multi-gigabyte SDK or a busy `/tmp` would otherwise refuse every run. A `.env` the walk did not reach there (a project kept under `~/go/src`, a checkout unpacked in `/tmp`) stays readable on Linux; macOS denies it by regex. A workspace in `/tmp` is its own root and is still walked whole.
   - **Interface and route lists are readable (deviation from the spec's family allow list).** seccomp lets `socket(AF_NETLINK, ..., NETLINK_ROUTE)` through, and no other netlink protocol: libc's `getifaddrs` needs it, and Node's `os.networkInterfaces()` (which dev servers call at startup) throws without it. It shows only the interfaces and routes of the sandbox's own network namespace (only `lo` with the network off or through the proxy; the host's, as with the network on, when the chat has network). Changing them needs `CAP_NET_ADMIN`, which the sandbox lacks. Netlink audit, uevent, netfilter and sock_diag fail with `EAFNOSUPPORT` (LNX-SECCOMP tests).
6. **Seatbelt's future.** `sandbox-exec` has been documented as deprecated for years and still ships. If it goes, the backend moves to `sandbox_init` in a small signed helper; the policy model does not change.
7. **Windows (MXC) is weaker than macOS and Linux.** DNS resolves in proxy mode (MXC#1666); single loopback ports, "no new processes" and hard memory or process limits are not available; Git Bash, MSYS2, Cygwin and WSL are refused (MXC#1061); start-up costs about 450 ms per command on the `windows-11-arm` runner (PERF-WIN-1), above the 300 ms budget, so Windows stays off by default.

## Limits of the policy

8. **The agent profile is deliberately weaker than the workload profiles.**
   - **Reads:** narrow (D-14), but wide: the system folders, the programs on PATH, the user's toolchains, the workspace, temp and the CLI's own state, with credentials denied on top. Not the rest of the home folder.
   - **macOS services:** it reaches system services, with the escape hatches denied.
   - **Keychain:** items readable by the `security` tool (Claude Code stores its login that way) are readable, because the agent needs its own and the Keychain's per-item access lists, not the sandbox, guard the rest.
   - **Network on:** when the chat's network is on, it has unfiltered network, including loopback services, which is the user's choice.
   - **`~/.ssh` with the network on (SSH-1, SSH-2).** For git over SSH the agent reads ssh's `config`, the files in `config.d`, every file a config `Include`s (outside `~/.ssh` too, as OrbStack and Colima add), the known hosts files (`known_hosts`, `known_hosts2`, each `UserKnownHostsFile`), and the public keys and certificates (`*.pub`, each `IdentityFile`'s `.pub` and `-cert.pub`, each `CertificateFile`), as named and at their real paths; it signs through the ssh-agent socket (macOS). The list is made at every launch, of files only, never a folder, so nothing added to `~/.ssh` later is readable, and it never holds a file whose first bytes are a private key (PEM, PKCS#8, OpenSSH, RFC 4716, PuTTY), whatever its name. Keys anywhere under `~/.ssh` (four folders deep, 2,000 entries, through links) are denied as named and at their real paths, with the network on or off. **Readable by design:** what those files say (the hosts the user reaches, user names, public keys). **Not readable:** everything else there (notes, tokens, `authorized_keys`, keys under any name), so a path written with `%` tokens other than `%d` is not followed, ssh can't save a new host's key to `known_hosts`, and a ControlMaster socket under `~/.ssh` can't be made. A private key in a format without one of those headers (raw DER) that a config names as a certificate or that is called `*.pub` would be readable.
9. **Exfiltration through the agent's own API channel cannot be stopped by any sandbox.** Whatever the agent can read, the model can repeat to its provider. Credential denies limit what it can read.
10. **Proxy filtering is by hostname, without TLS inspection.**
   - Domain fronting through an allowed CDN can carry other traffic.
   - A wildcard such as `*.example.com` lets the workload make the proxy resolve any name under that domain, which is a DNS channel when the attacker controls it.
   - Anything that ignores proxy variables (raw sockets, UDP, plain ssh) simply has no network.
11. **Hard links that already exist.** A hard link created *before* the run inside the workspace, pointing at a secret, is read by its workspace path; path-based sandboxes cannot see the inode. New hard links into denied folders are refused.
12. **Paths containing `"` or control characters are refused** rather than expressed (SBPL regex literals cannot carry a `"` safely).
13. **File access Volt performs for the agent (ACP `fs/*`, host tools) is checked, then performed** by Volt's own process, so a workload that swaps a folder for a symlink between the check and the operation could redirect it. **Reads and writes are now race-free** (`safeOpen.ts`, SEC3): the open itself follows no symlink (macOS `O_NOFOLLOW_ANY`; Linux the `volt-fsd` helper's `openat2` with `RESOLVE_NO_SYMLINKS`, or, without it, only existing files, with the descriptor's `/proc/self/fd` path checked), so a swap makes the operation fail, never land elsewhere (RACE-1..3, SEC3-3-RACE). **Delete is the one path still checked-then-acted:** Node exposes no `unlinkat`, so the file's parent is confirmed to be its own real path (no symlink) immediately before `fs.unlink`, which narrows the window but does not close it; a parent swapped to a symlink in the gap between that recheck and the unlink could delete a file outside the workspace (destructive only — no read, write or code execution). The recheck held across 500 deletes under a folder flipped 100+ times (SEC3-3-RACE-DEL, chatFiles and the files broker share the guard). A `volt-fsd`-style `unlinkat` helper would close it.
14. **Protected files can enter through git history.** An agent can commit `.vscode/tasks.json` or a hook manager's config into a branch (git objects are writable so commits work). Checking that branch out *outside* the sandbox materialises them. Volt reads worktree setup only from the main checkout, but other host tools that check out agent branches should treat them as untrusted.
15. **Worktree setup of an unsandboxed chat runs unsandboxed.** The setup *file* is trusted (read from the main checkout), but `npm ci` in a new worktree runs that branch's `package.json` scripts. A sandboxed chat's setup runs in its sandbox, with the worktree and its repository's `.git` as the workspace (LIFE-PATH worktree-setup).

## Pathways not covered yet

16. **Native in-process models: only their shell runs in the sandbox.** A native model's `shell` commands run in the chat's sandbox with its rules (LIFE-PATH-2, NATIVE-1), what the sandbox stopped shows as the chat's Volt Guard card (NATIVE-DENY-1/2), and a refused command is an error the model reads (FAIL-NATIVE-1). Its file tools run in Volt's process and are judged by the host-tool gate, not the OS (see item 13).
17. **Third-party extensions run unsandboxed unless the user turns on "Run in Sandbox"** (N.1: opt-in, macOS and Linux). An opted-in extension gets an extension host of its own in the OS sandbox (P2/P6; the desktop starts it through the local Volt server), restarted alone and never unsandboxed when it crashes. The window refuses that host the main-thread APIs that would act outside the sandbox (T3-ESC-1..9: shell terminals, typing into terminals it didn't create, tasks, debug sessions, terminal environments, `workspace.fs` through the window, workspace edits outside the workspace or into files that run code, commands that start or install something). Still open: (a) a debug configuration provider for one named type (`node`, `python`) can rewrite the user's own sessions of that type, which start outside the sandbox when the user presses Run; only the every-type `*` provider is refused, since a debugger extension needs its own type's provider; (b) public commands of *other* extensions run in their own (unsandboxed) hosts, and the refusal list covers VS Code's terminal, task, debug and extension commands, not every extension's command that may spawn something; (c) Windows has no sandboxed extension host.
18. **Volt's own stdio MCP servers** (`.mcp.json`, `.volt/mcp.json`). A repository's file starts a server only in a trusted folder and after the user approved that exact server (its digest, B-02; `mcpHost.ts`). For a sandboxed chat the server runs in that chat's sandbox under the supervisor (C6), refused rather than started outside it; for an unsandboxed chat it runs as the user, as before.
19. **Model probes and commit-message generation run agent CLIs unsandboxed**, as Volt's own work. A sandboxed chat's title runs in the chat's sandbox (LIFE-PATH-7). Text for no chat (commit messages, the git slot) runs in `/tmp`, away from any project, with tools, hooks, slash commands and MCP off (Claude), Codex's own read-only sandbox, or Cursor's ask mode: no project file is read or run, and the prompt is Volt's. Sandboxing them would cost a launch (about 45 ms) and an agent-state overlay per call for no gain in what they can reach, so they stay as they are.
20. **The relay runner** starts Claude with `bypassPermissions` and Codex with `--dangerously-bypass-approvals-and-sandbox`, with the full environment including the relay enrol key. Its container is the only boundary. **Next:** run it through `SandboxManager` (Linux) and strip its environment.
21. **The in-app browser's network.** A sandboxed chat's browser is a profile of its own (in memory, signed out; B-16): every request of it, page scripts and `browser_evaluate` included, goes through its own network broker route with the chat's rules (network off: the chat's allowed hosts and granted loopback ports; a request Volt can't tie to the chat is refused). Unsandboxed chats share the user's signed-in profile with no filtering. Not enforced: what a page already loaded sends to a host the chat allows (filtering is by hostname, item 10), and the `legacy` proxy mode (`volt.sandbox.networkBroker`) uses the earlier proxy with the same host rules.
22. **Reading other chats** (fixed for sandboxed chats): `thread_read`, `thread_wait`, `queue_list` and `worktree_status` reach only the caller's own chat and its subagents and side chats; `thread_list` lists only those; `thread_search` is refused (GATE-XCHAT-4). The `terminal_*` tools serve only the caller's own terminals. `workspace_status` reports what the user opened beside this chat in its right panel (which can include a terminal of the user's there). Unsandboxed chats keep reading every chat.
23. **Policy files apply at the next launch, and a missing one is guarded best effort on Linux.** `~/.volt/sandbox.json` and `.volt/sandbox.json` are loaded at every launch (02-design.md, "Policy files"); an edit does not reach a chat whose agent is already running. On Linux, bubblewrap can only protect paths that exist, so a sandboxed agent may create a missing `.volt/sandbox.json` (`filesystem.protectNew` is reported partial); macOS refuses it.
24. **Sandboxed terminals are the chat's agent terminals only.** A sandboxed chat's `terminal_start` (and a native model's long-running `shell`) starts on a PTY inside the chat's sandbox: a launcher opens FIFOs for the backend's confirmation, and the shell waits for a go line Volt types once the sandbox is confirmed (F.6, LIFE-PATH-1). Echo is off until the gate has read it, so the line never reaches the output (PTY-ECHO-1). A terminal the user opens from Volt's terminal panel is the user's own and runs unsandboxed, like any terminal app; a terminal that started outside a chat's sandbox cannot be typed into by that chat once it is sandboxed.

## Found in the 2026-11-09 review, not fixed yet

25. **A managed policy change takes up to a minute.** The execution host reads it again every minute and sends each change to the launcher, plugin hosts, the network broker and the windows' gates (ADMIN-LIVE-1); there is no file watch on `/etc/volt/policy.json` or the MDM domain.
26. **Fixed:** a sandboxed extension's tool flows are judged by its declared hosts plus the "Allow host" grants in the grant store (the broker's, unrevoked and unexpired, from any run), and a tool served from a sandboxed extension host is now owned as sandboxed (PERM-FLOW-2). A tool of an unsandboxed extension still counts as reaching every host.
27. **Settings-only comparison** (no scopes) still counts unknown folders as writing nothing; it is kept for settings math only. Every caller that compares two chats (subagents, automations, run groups, the orchestrator, `thread_send`) passes both chats' roots, so an unknown folder fails closed there (SCOPE-27a..c).
28. **Decision-log records an older Volt wrote replay without request proof.** Records now carry `v: 2` and a request digest, so an edited request is reported (POL-DET-2); version 1 records still replay and are counted as `unproven`. The digests are plain hashes, not keyed: they catch a careless edit, not someone who recomputes them. The plugin host is the only Authority that logs (`~/.volt/trust/decisions/`, DL-WIRE-1); a log that can't be written is warned about once and decisions go on unlogged, since the log is a record, not a gate.
29. **A grant store written by a newer Volt takes no new grants.** Revoking works there (GS-NEWER-3): revokes and dropped subjects go to `grants.revoked`, a log every version applies over the store; adding a grant stays refused.

## Found in the 2026-11-10 review (plugins and extensions), not fixed

30. **Built-in Volt extensions' capability declarations reach no runtime gate.** All 30 `extensions/volt-*` packages are manifests without code: their features run in the window as feature modules, which use Volt's services directly and never call their `host.plugin.volt` context. So `FIRST_PARTY_ENFORCED` judges a path no built-in takes, and a feature that used more than it declares would not be refused. What does hold: every declaration stays within its compiled ceiling (EXT-CEIL-CI-1), and the one built-in with sandboxed code, Memory's T2 plugin, uses only what it declares (`tools.register`, `agents.context`, its own storage). Routing feature code through its context is a refactor of every feature module, not a fix here.

## Found in the 2026-11-10 chat-sandbox round (R1), not fixed

31. **/usr/bin shims that fall back to `xcodebuild -find` fail on macOS** (`/usr/bin/pip3` when xcrun's cache has no entry for it): xcodebuild asks LaunchServices (`coreservicesd`), which stays denied because it opens apps outside the sandbox. `git`, `python3`, `clang` and anything installed by Homebrew, pyenv, nvm or uv work (TOOLCHAIN-MAC-1).
32. **Which denials get a card is judged by the process that made them.** Shell startup files read by a shell, `~/.npmrc` read by npm or node, `~/.netrc` read by git or curl, and the home folder or a folder above the workspace probed by anything but `ls`, `find`, `cat` and the like stay denied and are logged only (DENY-QUIET-1..4). The agent running `node -e "fs.readFileSync('~/.npmrc')"` therefore gets no card either: Seatbelt names the process, not who asked. Linux reports no kernel denials (item 5), so there only the shell files are quiet.
33. **A changed sandbox level applies from the chat's next turn.** The running turn keeps the agent process and sandbox it started with; its MCP servers stop at once (F.9), and the next turn starts a new agent under the new level.
34. **A config lock orphaned less than 10 s ago fails that merge-back.** The overlay's merge into `~/.claude.json` waits 5 s for the lock and takes over one not refreshed for 10 s; in between, that merge fails (logged) and the next one carries the same change (FAIL-LOCK-1).

## Found in the 2026-11-10 network round (R2), not fixed

35. **A chat's proxy credential is readable by any process of the same user on macOS.** Seatbelt can't hide another process's environment (`sysctl KERN_PROCARGS2` passes even an explicit `sysctl-read` deny), and agent CLIs are not platform binaries, whose environment macOS hides. Another chat with network off still can't use it: only the chat's own sandbox reaches its route's port, and the route refuses every other route's token with an audit event naming whose it was (NET-E2E-7, NET-E2E-4, NET-12). A process with an open network (a chat with network on, anything unsandboxed) can reach the port and use the token; it gains no network it lacks, but its requests count against that chat's budgets and show in its denial cards. **Next:** verify the connecting peer (its pid's sandbox) per connection, within the 2 ms budget.

## Found in the 2026-11-13 security round (R4)

36. **Files that something unsandboxed runs later: what stays writable, and why** (EXEC-LATER-1). A sandboxed chat can't plant or change git's config, hooks, `info/`, alternates, `commondir`/`gitdir` or a new `.git` (B-03, PERS-1..3); `.vscode`, `.idea`, `.devcontainer`, `.envrc`, `.mcp.json`; hook managers (`.husky`, `.githooks`, `.pre-commit-config.yaml`, lefthook); Claude's settings, commands, agents, hooks and skills; Gemini's settings, commands and extensions; Codex's `config.toml` and `hooks.json`; Cursor's MCP and hooks; Volt's hooks, MCP and worktree setup; Zed's settings and tasks, Helix's `languages.toml` and `config.toml`, and `.nvim.lua`/`.nvimrc`/`.exrc`, at the project's root. Volt's own git runs through HostGit (no fsmonitor, hooks or `ext::`), its tasks and debug tools are refused for a sandboxed chat, and Run, worktree setup, Commit and Push show the build-entry guard's diff first (I.6). **Writable by design:** `package.json`, Makefiles, `.npmrc` and `.yarnrc.yml` (the guard shows their changes before Volt runs them; a command the user types in their own terminal runs them without asking, as it would after any `git pull`); `.github/workflows` (runs on the CI host after a push the user makes, and shows in the diff); `.gitattributes` and `.lfsconfig` (they name filters and URLs, not commands: a filter's command lives in git config, which is protected); `*.code-workspace` and a `.vscode` folder below the root (VS Code reads them only when that file or folder is opened, which is the user's act); `AGENTS.md`, `CLAUDE.md` and rules files (instructions the next agent reads under its own permissions, not code). Linux guards only what exists at launch (item 3).

## Future work, in order

1. Native models' file tools in the sandbox (item 16): today only their shell runs in it.
2. Capability manifests in extension packages and the open parts of item 17: the start of the marketplace.
3. Windows: an x64 runner for the WIN-* suite, packaging `wxc-exec.exe` and `volt-mxc-helper.exe` with the app, and Git Bash on the AppContainer-compatible MSYS2 runtime once its distribution is decided (WIN-MSYS-2 passes in CI).
4. Supply-chain pipeline extension points, which the sandbox does not block:
   - package integrity (a hash lockfile);
   - publisher identity and signed artifacts (Sigstore or Volt-signed);
   - dependency analysis and an install-time scan for hidden Unicode;
   - capabilities declared in the manifest and diffed on every update;
   - update verification.
5. cgroups v2 limits on Linux; a signed macOS helper for `sandbox_init` and process sweeps.
6. "Cells": copy-on-write workspaces with review on exit, as a strict opt-in mode.
