# Grok critique (round 2)

Lens: OS core, backends, Windows, escape paths. All five proposals were read (`proposals/grok.md`, `claude-a.md`, `claude-b.md`, `sol.md`, `terra.md`). Code checks are against this checkout (`main`) or `git show feat/volt-sandbox:<path>`. Line numbers for the branch are from that show.

## Objections

### 1. Claude A §6.4 and §4 — a failed sandbox promotes first-party code into the TCB

**Claim.** W4: "A T2 plugin that fails to start falls back to its T1 build of the same code for first-party only." §4: on Windows older than the MXC floor, first-party T2 still runs, shown as `partial` with `unenforced: [filesystem, network]`, held up by Node `--permission` and SES. §2.3: "T1 has no OS profile."

**Why it fails.** `feat/volt-sandbox` `SandboxManager.prepare` throws `SandboxUnavailableError` when the backend is unavailable or a used dimension is not enforced (`sandboxManager.ts` probe + `checkEnforcement`). A fallback that loads the same module in-process is the silent retry F-01 forbids, aimed at the features that hold tokens (`volt-usage`, provider hooks, `volt-memory`). Node `--permission` is a library inside the process. It is not a token, a job, or a WFP filter. Marking filesystem and network `unenforced` and continuing is the opposite of the branch's enforcement check. The W4 sentence also makes every future confirm bug a privilege upgrade: the host fails closed, then Volt opens the unsandboxed copy.

**Attack.** Windows 10, or Windows 11 below `26100.9278`, or a supported build whose MXC trial returns `broken`. `volt-usage` (Claude A §6.3 row 17, end tier T2) fails `startHost`. The fallback activates the T1 module. That code lives in the server or the renderer (`platform/voltUsage`, which already fetches with OAuth tokens). T1 has no Seatbelt, no bwrap, no AppContainer. The module, or a bug in it that the import lint does not catch at runtime, executes `fs.readFile` of `%USERPROFILE%\.ssh\id_ed25519` and `fs.readFile` of `%USERPROFILE%\.claude` credentials. The same path dumps the volt-server HMAC secret, because the fallback runs in the process that holds it. Third-party plugins are refused on that OS; first-party plugins, which the user cannot turn into "not code," are the ones that run wide.

### 2. Claude A §2.2–§2.3 — "spawn: none" is not what the branch does, so the SES-escape argument is one layer short

**Claim.** The T2 `plugin-host` profile sets `process.spawn: "none"` and `limits.processes: 1`. "bwrap: seccomp denies `execve`/`execveat` after a ready marker, as the branch already does." An SES escape "yields only the RPC channel."

**Why it fails.** The branch filter is a denylist. `seccomp.ts` blocks `ptrace`, `process_vm_readv`/`writev`, namespace `clone`, `clone3`, `TIOCSTI`/`TIOCLINUX`, and optionally `socket(AF_UNIX)`. It then `SECCOMP_RET_ALLOW`s. `execve` appears only as a number in `seccomp.test.ts`. Nothing in `src/vs/platform/voltSandbox` denies it. Seatbelt `(deny process-fork)` / `(deny process-exec)` is not generated for this profile either; the agent profile does the opposite (`seatbelt.ts` `(allow process-exec process-fork)` under `(allow default)`, and `(allow process-exec process-fork)` under deny-default). Shipping "the branch filter" as "no spawn" leaves `child_process` working inside the namespaces.

**Attack.** A T2 worker escapes SES (or simply gets `require` because lockdown missed one intrinsic). It `spawn`s `node` from the read-only mount Claude A grants, `${volt.appRoot}/out`. That child is still in the bwrap namespaces, so this is not a full escape, but it is a shell the proposal counted as impossible. The child inherits fd 3, the process-wide RPC socket, and speaks as the publisher. On the Windows "partial" host from objection 1 there is no namespace at all, so the same `child_process` is a normal user process and the spawn reads `id_ed25519` directly. The profile cannot be patched later by "turning on the deny the branch already has." The deny has to be written, and it has to be parent-observed: a filter that is not installed must fail `confirm`, not log `partial`.

### 3. Claude A §4 — Landlock from `main` is a credential read, not an extra layer

**Claim.** Linux keeps "Landlock as an extra layer where kernel ≥ 5.13 (main already has `common/landlock.ts`)." AppArmor-blocked user namespaces get "an AppArmor profile" as the thing that makes bwrap work.

**Why it fails.** This checkout's helper is explicit: reads stay open; network exists only on Landlock ABI 4 (Linux 6.7); without user namespaces the helper "carries on and warns"; without Landlock "the agent runs unsandboxed with a warning, unless `--require`" (`src/vs/platform/voltSandbox/common/landlock.ts:12-21`). The old `bwrapArgs` in that same file `--ro-bind`s `/` and does not `--unshare-net`. The branch's `common/bwrap.ts` is a different program (user, pid, ipc, uts, net namespaces, `--disable-userns`). Calling the `main` helper an extra layer, or the fallback when userns is blocked, deletes the secret hide and the netns. Sol §4 is right to refuse that fallback. Claude A cites the file anyway.

**Attack.** Ubuntu 24.04 with `kernel.apparmor_restrict_unprivileged_userns=1` and no packaged profile yet (Claude A marks the profile a guess). Probe falls through to the `main` helper. ABI is 3, so the helper's own comment applies: network stays open, reads stay open, missing namespaces warn and continue. The agent runs `cat ~/.ssh/id_ed25519` and `curl http://169.254.169.254/` with no proxy. `~/.aws/credentials` is readable for the same reason. A kernel with no Landlock at all takes the last sentence of that comment and execs the agent as the user. That is the path `UnsupportedBackend` on the branch exists to close.

### 4. Claude B §2 and §4 — "language sandbox only" is a thread inside the monitor; the full-access click is the Windows backend

**Claim.** "Where the OS backend is missing (Windows without MXC), T2 still runs with SES alone, and that is the reason T2 is the default tier: it degrades to one layer instead of none." T2 is "Node `worker_threads` on volt-server/desktop utility." A third-party VS Code extension on unsupported Windows "runs only after the user acknowledges 'This extension will run with your full access'."

**Why it fails.** A `worker_threads` worker is the volt-server process. DeepSeek's second hole in CVE-2026-82533 was `run_code` on a worker thread outside the sandbox (brief §4). SES does not give that thread a different uid. Desktop `utilityProcess` cannot be wrapped: `ExtensionHostStarter.createExtensionHost` constructs a `WindowUtilityProcess` (`src/vs/platform/extensions/electron-main/extensionHostStarter.ts:77` on this checkout). Seatbelt, bwrap, and `wxc-exec` have to be the parent of the spawn. They cannot be applied after Electron has forked. The full-access acknowledgement is an unsandboxed Node host with the user's token. It is today's VS Code, which is the threat model, not a mitigation.

**Attack.** On Windows 10 the user installs a theme or a Python extension because the dialog says the words "full access" once. `activate` runs `fs.readFileSync(process.env.USERPROFILE + '\\.ssh\\id_ed25519')` and posts it to the extension's update host. No MXC, no sandbox-user, no WFP. Separately, a first-party T2 worker hosted in volt-server "because MXC is missing" shares the server heap. A bug that hands the worker the real `process` (or a V8 bug, which SES does not contain) reads the pairing token and the HMAC secret out of the server, then `child_process.spawn`s unsandboxed, because the server is allowed to. Labeling the badge "language sandbox only" does not change the address space.

### 5. Terra §2 and §9 — one host, then a shared pool, and the main thread trusts the extension id

**Claim.** T2 is "one OS-sandboxed Node plugin host" per window, one Compartment per plugin. T3 is "one sandboxed ext host per publisher (cap 8, then shared untrusted pool)." §5 tells those compartments apart by "the token their Compartment's `fetch` endowment adds."

**Why it fails.** Compartments and a pool share an address space and one OS profile. The profile is the union. Identity inside that process is whatever the untrusted isolate sends. This checkout already does that for secrets: `MainThreadSecretState.$getPassword(extensionId, key)` (`src/vs/workbench/api/browser/mainThreadSecretState.ts:38-47`) reads `secretStorageService` for the id in the RPC payload. It does not compare that id to the extension host Volt spawned. Claude B AT-10 guessed this; the code confirms it. A pool after eight publishers means the ninth extension is in a process with someone else's token, and the main thread will fetch that token on request. The endowment-added proxy token has the same shape: the secret lives in the isolate that is supposed to be confined by it.

**Attack.** The user has the GitHub Pull Requests extension (a stored token) and eight other publishers, so the next install, a "JSON formatter" from Open VSX, lands in Terra's untrusted pool with the GitHub extension. The formatter calls the ext-host secret proxy with the GitHub extension's id and key. Main returns the token. The formatter writes it into the workspace as `.vscode/settings.json`, which the chat then reads. OS filesystem denies on `~/.ssh` never run, because the read was performed by the main process on the extension's behalf. The same pool lets the formatter monkey-patch `vscode` and wrap the GitHub extension's `exports`. For T2, a single V8 bug in any compartment reads every other compartment's proxy token out of the heap and CONNECTs as the plugin that was granted `api.github.com`.

Claude A's §2.2 avoids the all-third-parties pool and then recreates it for the publisher `volt`: every first-party plugin shares one process and one fd 3. A bug in `volt-visuals` (agent-authored HTML, 21k lines, Claude A §6.3 row 27, end tier T1 in the same program as the later T2 set) forges a `volt-usage` or `secrets.get` call on that channel. Core cannot tell the workers apart once SES is gone, which Claude A §2.2 already admits.

### 6. Terra §4, §3.5, and §7 — Git Bash has no backend, and the refuse dialog runs it as the user

**Claim.** MXC is the only v1 Windows backend. sandbox-user waits for "PR 25, only if Windows-10 demand is real," behind `volt.sandbox.windows.legacyBackend`. The refuse UI offers "Run outside sandbox (this time)" for every principal (§3.5). First-party hosts run `audit: true` for two releases, and `audit: true` means "denials are logged but not blocked" (§3.3). §4 itself says agents on Windows live in Git Bash and that MSYS2 crashes with `0xC0000005` inside MXC.

**Why it fails.** The crash is not a Windows 10 problem. It is the shell Volt's agents already use on supported 24H2/25H2 (brief §4, srt PR #766). A chooser with no `msys`/`cygwin` image class launches `C:\Program Files\Git\bin\bash.exe` under ProcessContainer, the process dies, confirm fails, and the only button that produces an answer is the unsandboxed one. That button is then the Windows agent backend. Putting it on the same dialog as a failed confirm makes a broken or malicious probe look like a permission prompt. `audit: true` on the policy is the same hole with no prompt: if the backend honors the flag, the profile's denies do not fire. Two releases is a long time to ship a monitor that logs `open("~/.ssh/id_ed25519")` and returns the bytes.

**Attack.** Windows 11 25H2, Git for Windows installed, sandbox mode enforce. The chat starts Claude Code, whose Windows entry is bash. MXC faults. The transcript shows Terra's refuse card. The user clicks "Run outside sandbox (this time)" because the alternative is no agent. The repo's `README` has told the model to print the deploy key. `cat ~/.ssh/id_ed25519` runs as the logged-on user. Nothing in WFP, the job object, or the AppContainer sees it. The same card is how a VSIX that declares `limits.processes` as required (unsupported on macOS, `seatbeltBackend` notes) gets unsandboxed on a Mac: every launch refuses, the button is the product. During the audit window the click is unnecessary: `volt.usage`'s host is an enforced-looking process whose denies are recorded and allowed, and the prompt-injected tool reads the key through the host.

The confirm canary in the same section does not catch this. "Right after the host is up, before it gets any work, it tries `connect()` to a public IP" only works if the parent sees the packet or the prologue writes the result before user code. A canary the workload reports is a lie the workload can tell. The branch's confirm is the parent reading the prologue (`confirmFromStatusPipe` in `seatbeltBackend.ts`) and, on Linux, namespace inodes plus `NoNewPrivs`. Keep that. Do not replace it with a self-test.

### 7. Sol §5 — SOCKS5 UDP ASSOCIATE and a second DNS lookup undo the pin

**Claim.** v1 of `NetworkBroker` supports HTTP forwarding, HTTP CONNECT, and SOCKS5, including "SOCKS5 UDP ASSOCIATE" for explicit destinations. "Re-resolve for each new connection with a bounded TTL."

**Why it fails.** The branch proxy is HTTP CONNECT and plain HTTP on `127.0.0.1:0`. `destination()` looks up once, refuses if any answer is private, and `tunnel` connects to `target.address` (`feat/volt-sandbox:src/vs/platform/voltSandbox/node/sandboxProxy.ts:110-126`). There is no second lookup and no UDP parser. SOCKS5 UDP ASSOCIATE is a second address in a datagram header (RFC 1928 address types: IPv4, domain, IPv6). That header is the bypass of the TCP allowlist. A TTL cache plus "re-resolve" is how a check and a connect drift apart if any caller passes the name to `net.connect` instead of the address already checked. Sol's own §11 lists UDP spoof, fragment, and port smuggling as tests, which is the reason not to put that parser in the first broker.

**Attack.** A plugin, MCP server, or agent is granted `example.com` on TCP/443, which is a normal "Allow host." It opens SOCKS5 and sends UDP ASSOCIATE, then a datagram whose header is address-type `0x01`, destination `169.254.169.254`, port `80`. The TCP session was authenticated and allowed; the UDP header was not the thing the grant named. A short bug (treat the control connection's grant as covering the datagram, or accept IPv4-mapped `::ffff:169.254.169.254`, or a length field that shifts the address) delivers the cloud metadata document into the sandbox. The same datagram to `8.8.8.8:53` is a DNS exfil channel the OS was supposed to have no route to. Rebinding variant: the broker checks a public A record, caches it for the TTL, and a later connect looks the name up again (or connects by name) after the attacker has flipped the record to `127.0.0.1` or `10.0.0.1`. The branch's one-lookup-then-connect-to-that-IP does not have this gap. Don't add it.

Sol §4 also has no image class. "MXC via `wxc-exec` on supported builds; Windows 10 refuses" launches Git Bash under MXC. The process access-violates. The follow-on patch, once agents "don't work" on Windows, is retry unsandboxed. That patch is objection 6. The chooser has to know `msys` before the first Windows PR, not after the crash reports.

### 8. Claude B AT-5, Terra §6.3, Claude A provider env — `VSCODE_*` is not stripped, and caller env is the wrapper's env

**Claim.** Claude B AT-5: "sbx: unix sockets denied, VSCODE_* stripped (F-03). Holds for agents." Terra §6.3: a provider plugin returns `launch()` with `env (non-secret)` and core spawns it. Claude A §6.2: `secrets.get(key): Promise<string>` plus provider hooks that run with `process.exec`.

**Why it fails.** Stripping applies to `inherit: ["*"]` via `isSecretEnvName`. It does not apply to `env.set`. Untrusted `narrow()` drops reserved names and injection names (`LD_*`, `NODE_OPTIONS`, …) and then assigns the rest (`feat/volt-sandbox:src/vs/platform/voltSandbox/common/sandboxComposition.ts:225-232`). `VSCODE_EXTHOST_IPC_HOOK`, `NODE_CHANNEL_FD`, and `ELECTRON_RUN_AS_NODE` match neither `isReservedEnvName` nor `isInjectionEnvName`. `sandboxResolver.ts:272-280` then applies `policy.env.set` and `context.env` with the same reserved-only check. `context.env` is `options.env` from `VoltSandboxLauncher.prepare`, and that `env` object is the environment of the spawned command. The spawned command is `bwrap` or `sandbox-exec` or, later, `wxc-exec`, not only the inner agent. `LD_PRELOAD` on that environment is loaded by the wrapper, which is still the user, before the sandbox exists. macOS SIP strips `DYLD_*` from `/usr/bin/sandbox-exec`. It does not strip `LD_PRELOAD` from `bwrap`, and it will not strip a DLL search against `wxc-exec`.

Policy files are not loaded yet (brief §3). Terra PR 3 loads `.volt/sandbox.json` as an untrusted layer. That is the moment the `env.set` hole becomes a repo file. Provider `launch().env` becomes the hole without waiting for PR 3, because it arrives as `context.env`.

**Attack.** A cloned repo contains `.volt/sandbox.json` with `env.set.VSCODE_EXTHOST_IPC_HOOK` pointing at the socket the unsandboxed extension host is listening on, and `env.set.NODE_CHANNEL_FD=3`. Terra PR 3 composes it. `narrow()` keeps both names. The agent process receives the real IPC path. Where the profile still has a unix socket or a Windows named pipe (the agent `(allow default)` profile, or a T3 host that must keep its own pipe), it connects and uses the `launch` channel. Even with `AF_UNIX` blocked, the second half fires: a third-party provider, or a compromised first-party one, returns `env: { LD_PRELOAD: "<workspace>/evil.so" }` from Terra's `launch()`. Core passes it through `prepare`. `bwrap` is exec'd with `LD_PRELOAD` set. `evil.so` runs as the user, reads `~/.ssh/id_ed25519`, and writes it under the workspace. `secrets.get` makes the exfil boring: the same provider calls `secrets.get('anthropic')`, receives the raw token the signature pre-granted (Claude A §6.2), and the model pastes it into the tool result. Claude B's rule (the broker injects the header, the plugin never sees the value) is the one that closes this. Claude A's `net.fetch({ auth: secretRef })` says that, and `secrets.get` undoes it.

Claude A's §5 SNI peek ("matching SNI to CONNECT host" as the domain-fronting mitigation) is the same class of mistake as Sol's extra parser. CONNECT to an allowed CDN with a matching SNI still routes the inner `Host` anywhere that CDN fronts. The peek does not stop that, and a ClientHello parser in the broker is another place a length field becomes a tunnel desync. Leave TLS opaque. Name the CDN grant as exfil-capable, which Claude B AT-8 and Terra §5 already say.

## Concessions

I adopt these, and I drop the round-1 wording where it conflicts.

- **Signed ceilings, not allow-all.** Claude B §7.3. A first-party signature pre-grants the manifest's capabilities only when they are inside a ceiling table compiled into the core binary. Widening the ceiling is a core release. Zero prompts. I already rejected `sandbox: false` for T1; the ceiling table is the concrete form of that, including the Android privapp-allowlist shape. Claude A §7.1 (declared, auto-granted, still enforced) is the same rule without the table. The table is what stops a stolen plugin key from growing the grant.
- **Caller attenuation.** Claude B AT-6. Effective rights for a call are plugin grants ∩ caller grants. An agent that is itself sandboxed does not get to use `volt.automations` or `volt.computer-use` at the plugin's ceiling. Allow-all makes that intersection meaningless. I should have written this into the host-tool gate instead of leaving it as "T1 is pre-granted."
- **No raw secrets.** Claude B §10 and Sol's secret handles. `secrets.get` returning `string` is withdrawn. Header injection and one-shot launch handles only.
- **Per-publisher OS process, parent-owned ports, never a shared third-party host.** Claude A §2.2's identity rule (the channel is the identity, a `pluginId` in the payload is ignored) is right. It does not extend to putting every `volt.*` plugin on one channel. Unequal ceilings get unequal processes. Terra's cap-8 pool is rejected. Sol §13's "never pool third parties" is adopted.
- **Providers describe, core spawns.** Terra §6.3. A provider plugin must not receive `process.exec` of the agent CLI. Core calls `SandboxManager`. The plugin's launch spec may name a command and args. It may not supply the environment of the wrapper (objection 8).
- **Merge and harden the agent sandbox before moving feature code.** Terra §0. The user asked for migration first. The code does not support that order: today's desktop host is a `utilityProcess`, today's server host is an unsandboxed `cp.fork` (`extensionHostConnection.ts:277`), and the 30 `extensions/volt-*` are empty manifests. Moving `volt-usage` into that host makes it worse. I change round 1's sequence to match Terra here: land `feat/volt-sandbox`, fix the env overlay and the Windows chooser, then move features behind the facade.
- **Only network grants widen a live OS profile.** Terra §3.7 and Claude A §3.6. Files, spawn, and sockets relaunch or go through a broker. I keep my round-1 `allow()` for hosts. I add Sol's compare-and-swap: the UI sends `denialId` and the policy revision; the execution host rebuilds the rule from the denial it recorded. A phone or a webview cannot swap in a different host (Sol §5 and §13).
- **Kernel-selected broker route, not a header.** Sol §5. One loopback port per principal in that principal's Seatbelt/WFP rule, or one unix socket in that netns. `Proxy-Authorization` is defense in depth. The route is the identity. Terra's "the compartment adds the token" is rejected.
- **Metadata, loopback, and LAN stay split.** Sol §5 and Claude B §5. I already had this. I adopt Sol's extra: LAN permission still does not include `169.254.169.254`, link-local, CGNAT, or the host gateway.
- **Do not fall back to Landlock.** Sol §4. Objection 3.
- **Windows operations.** Terra §4: pin `wxc-exec` with `WinVerifyTrust` and a file hash; do not assume GitHub-hosted `windows-2025` can run ProcessContainer; a self-hosted 25H2 runner is required before MXC is a required check; a Git Bash smoke test is an acceptance test, not a follow-up. The smoke test is how we prove the chooser picked sandbox-user, not how we decide to unsandbox bash.
- **Signing facts from Claude B §7.1.** The update feed is unsigned JSON, the sha256 comes from that same feed, missing certs mean ad-hoc macOS and unsigned Windows, gallery `NotSigned` is not a failure. I am not restating the TUF tree. I accept it as the signing design, and I accept that a remote kill switch must not ship before that feed is signed. A switch that can move `enforce` to `ask` on an unsigned feed is a network attacker with a sandbox-disable button (Terra §12 vs Claude B §7.1).
- **Fuses and signals.** Claude B AT-5: `--disable-sigusr1` on every Node host (Node 22.14+, Electron 37 is 22.19), and turn off `EnableNodeCliInspectArguments` and `EnableNodeOptionsEnvironmentVariable` in release builds. An inspector on `127.0.0.1:9229` plus a sandbox that can reach loopback is a second shell.
- **Declarative UI and confirm-before-RPC.** Claude A §2.5 and §3.4. The host does not get fd 3 until `confirm()` has succeeded. Iframes have no `connect-src`. I drop round 1's implication that a first-party in-process module is an acceptable end state for anything that parses repo or model HTML.

I do not adopt: T1/T0p as the steady state for `visuals`, `pull-requests`, `automations`, or `usage`; `audit: true` as a policy bit; "Run outside sandbox" on a failed confirm; SOCKS5 or UDP in v1; SNI inspection; sandbox-user as a silent fallback from a failed MXC trial; SES-only or `--permission`-only as a reported sandbox level.

## Revised position

| Decision | Revised position |
|---|---|
| Windows backend | Unchanged chooser, with Terra's test rig. MXC ProcessContainer via pinned, Authenticode-checked `wxc-exec` for PE images on the brief's build floor. sandbox-user (separate install, never the recovery path for a failed MXC trial) for two cases only: the OS cannot run ProcessContainer, and the image is MSYS2/Git Bash/Cygwin (`0xC0000005`). `wsl.exe` refuses on both. No image class of `unknown` is treated as PE. Windows 10 with sandbox-user installed and probed is a real backend, not a "later if demand" flag. A failed confirm or a `broken` trial kills the run and does not offer "Run outside sandbox." A user who wants an unsandboxed chat sets the chat level off, which is a different control from a failed enforcement check. GitHub-hosted Server images run the refuse tests only. Adversarial MXC and the Git Bash smoke test run on a self-hosted Windows 11 25H2 runner. |
| First-party allow-all | Rejected, including my round-1 phrase where it could be read as "the process may be wide." Signature plus `publisher: volt` pre-grants the manifest, intersected with a ceiling table baked into the core binary at build time (Claude B). The OS profile is compiled from that intersection and is always enforcing. There is no `audit` bit, no two-release log-only window, and no fallback to an in-process copy when `startHost` fails. The user sees no prompt. A capability the ceiling does not list is dropped, not prompted. Critical desktop, screen, and secret-manage rights stay on helpers with per-chat approval and are attenuated by the calling chat. |
| Host tiers | T0 is the monitor: renderer, Electron main, volt-server, `SandboxManager`, brokers. It is not a place plugin code runs. T2 is the default for Volt-native plugins, first-party included: one OS-sandboxed process per plugin (per publisher only when every plugin in it has the same ceiling and the parent holds a separate port per plugin). SES inside that process. The process has its own broker route. No `worker_threads` inside volt-server or inside a `utilityProcess`. T3 is one sandboxed `bootstrap-fork` per extension, started by `SandboxManager` from volt-server, not by `WindowUtilityProcess`. The main thread stamps identity from the host it spawned; `extensionId` in a SecretStorage RPC is ignored. T0p in-process UI is allowed only for code that does not parse attacker HTML or hold tokens. Agent HTML stays in an opaque iframe. `visuals`, `usage`, `automations`, and provider hooks do not end as T1. Computer-use, devices, and speech stay helper processes with a parent-side socket, not renderer modules with a facade. |
| Migration order | Terra's order, not the user's literal order, and not Claude A's W4 fallback. (1) Merge `feat/volt-sandbox` after the user agrees. (2) Fix `sandboxResolver.ts` so `policy.env.set` and `context.env` both go through `isSecretEnvName` and `isInjectionEnvName`, and so the wrapper (`bwrap`, `sandbox-exec`, `wxc-exec`) is spawned with a Volt-built environment, not the workload's. (3) Windows chooser and the Git Bash test. (4) Facade and capability checks in enforce mode, never log-only. (5) Move process-shaped features into T2 hosts one at a time, old `contrib/` path still compiled until that host is the default. (6) Only then T3 for Open VSX. A feature whose host cannot confirm does not run. Providers register a launch description; they do not spawn. |
| Network broker | The branch proxy stays the v1 broker. One HTTP proxy endpoint per principal, bound by the OS rule to that principal, `Proxy-Authorization` as a second check, DNS pin exactly as `sandboxProxy.ts:110-126` (one lookup, every address public, connect to the checked IP). No SOCKS5, no UDP, no QUIC, no ClientHello parser, no TLS MITM. `none` / `proxy` / `public` / `host` as in my round 1. Loopback ports, LAN, and public names are different capabilities. Metadata and link-local stay denied under LAN. "Allow host" is `denialId` + revision, applied live, and it cannot name a private address. Linux `host` for an untrusted identity stays refused if we cannot deny Volt's own ports without a supervisor (my E18); `public` is the ceiling there. |
| Signing | Claude B's TUF layout: offline root, release key in a protected environment, first-party plugins signed against a ceiling id, revocation key can only revoke. I do not redesign it. What the OS core requires from it: the ceiling hash is inside the signed app, a plugin update that asks for more than its ceiling does not load, and the unsigned `volt-update-feed` cannot carry a sandbox kill switch until the feed is on that tree. Dev mode and Playground drafts are unsigned, banner-visible, and never pre-granted. A signer change drops grants. `builtin` location is not trust by itself; the hash list Claude A §7.1 describes is necessary because a user-writable install directory on Windows can replace a bundled extension's `out/`. |
